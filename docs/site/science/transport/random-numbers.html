Where do the random numbers come from?

Transport

A "random" number in a Monte Carlo code is not random. It is the next number of a fixed sequence that merely looks random. That is a feature: the same seed gives the same run, every time.

The generator

The code uses OpenMC's generator (Romano et al., 2015), in the petir crate (petir::rng::lcg, outram_mc_libs::rng::lcg re-exports it). Its state is a 64-bit integer advanced by a linear congruential step, wrapping at 264:

x ← 6364136223846793005 x + 1442695040888963407  (mod 264)

The number handed out is not the state. A raw LCG's outputs fall on a small number of planes when you look at consecutive draws together, which is exactly what a history does (a distance, then a direction, then an energy). So the state is passed through the PCG-RXS-M-XS output permutation (a data-dependent shift, a multiply, a final shift) before it is turned into a number in [0, 1). The recurrence is untouched by the permutation, so the jump-ahead below still works.

Starting from the seed 1 the first draw has the 64-bit pattern 0x3fe6bf040c43dded and the state after four draws is 0x620355cd119357c5. Those are not computed on this page and compared with themselves: they are the values pinned in the Rust crate's own test, moved_stream_is_pinned (crates/petir/src/rng/lcg.rs:278), and check-transport.js recomputes them with the 64-bit integer port used by the widget below. The same check confirms the mean, variance and a 100-bin chi-square of a million draws.

Jumping ahead

Because the step is linear, n steps compose into one step with a different multiplier and increment, which can be found in about log2 n operations (future_seed, Knuth's method). So the code can place a stream n draws further along without drawing those n numbers. That is what lets every history have a stream of its own.

  • Each generation g starts 240 draws on from the run's master seed (GEN_STRIDE).
  • Each history h of that generation starts h × 152 917 draws on from the generation's start (HIST_STRIDE, the same per-particle stride OpenMC reserves). No history uses 152 917 draws, so neighbouring streams do not overlap, and 240 is far more than a million histories' strides (a check on this page: the ratio is 0.14).

So history h of generation g depends only on (master seed, g, h), nothing else. It does not matter which worker transports it, or when.

Predict first: in the toy below, a thousand histories each draw five numbers. Serve them with 1 worker, then with 4 workers that finish in a shuffled order. How many histories get different numbers when each has its own stream? When all share one stream?

Why reproducibility earns its keep

  • Regression tests. A test that pins a k to a seed (as the crate's tests do) fails the moment anything that should not have changed an answer does. That is how a refactor is proved to move nothing: the same seed gives the same digits, as the move of the generator from outram-mc-libs to petir was (it changed no random number).
  • Debugging. A bad history can be replayed alone: its seed is a function of (seed, generation, history), so the code can restart exactly it (particle_restart.rs documents history_seed = future_seed(hist_idx * HIST_STRIDE, gen_base_seed)).
  • The answer does not depend on the number of workers. The multi-threaded run (run_keff_csg_par) and the browser demo's pool of Web Workers give the same k, bit for bit, for any number of workers (the pool is transport_csg::distributed; the page-11 demo's whole-core run records it).

A known defect: streams that alias

Everything above is how the transport stream of each history is laid out. The code also gives each history three auxiliary streams by jumping a small multiple of the stride on from its own seed: one for the delayed-neutron group (3 strides), one for the unresolved-resonance probability bands (5 strides) and one for a split child under weight windows (1 stride). Those jumps land where other histories' transport streams start: history i's resonance-band draws are history i+5's transport draws. The widget's arithmetic shows it, and check-transport.js asserts it of the layout. OpenMC avoids this by starting each stream of a particle from a different master seed. This is an open issue, gh:#700 (audit of 2026-10-06, as of this page's commit). Its effect on k has not been measured: each history still sees uniform numbers, so the mean is unaffected, but neighbouring histories are not fully independent, and the quoted error bar assumes they are (page 10).
