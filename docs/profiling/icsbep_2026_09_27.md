# Profiling the four ICSBEP benchmarks, 2026-09-27

Where the time goes in the four criticality benchmarks on the HIGH
(continuous-energy ENDF/B-VIII.0) path, what was fixed, and what is left.

| case | ICSBEP | example |
|---|---|---|
| Godiva | HEU-MET-FAST-001 | `godiva_keff_endf_local` |
| Jemima | IEU-MET-FAST-002 | `jemima_keff` |
| HST-009 | HEU-SOL-THERM-009 case 1 | `hst009_keff` |
| LCT-008 | LEU-COMP-THERM-008 case 1 | `lct008_keff` |

`godiva_keff` (the embedded WMP + 10-group LOW tier) was deliberately **not**
profiled: it shares nothing with the other three below the driver, so its
profile would not inform theirs.

## Methodology

- **Instrument 1, sampling (all phases).** `perf record -e cpu-clock -F 499 -g`, frame-pointer
  call stacks, folded with `inferno-collapse-perf` and drawn with
  `inferno-flamegraph`. The software `cpu-clock` event is used because the
  VM exposes no hardware PMU. Percentages are of **CPU time summed over all
  threads**, not of wall time.
- **Instrument 2, callgrind (transport only).** `valgrind --tool=callgrind
  --instr-atstart=no`: data preparation runs uninstrumented, and
  `callgrind_control -i on` switches instrumentation on when the example
  prints its `histories/gen` line, just before transport. Reduced statistics,
  500 histories x [20 + 5] generations, because callgrind runs 50-100x slower;
  it measures the cost structure per history, not k. Its counts are exact
  instruction counts (`Ir`), independent of machine load.
- **Build.** The workspace `profiling` Cargo profile: `inherits = "release"`
  plus `debug = "line-tables-only"`, and `-C force-frame-pointers=yes`.
  (These runs used that setting. On merging `develop` the same day, the
  profile became `debug = 2` and `strip = "none"` from `7fac86116`. Debug
  info does not change the generated code, so these numbers still apply.)
  Frame pointers reserve a register, so this build is a few percent slower
  than `--release`. Its physics is the same: every benchmark's k was
  identical to the digit before and after the fix (below).
- **Runs.** Each example's **default** configuration (LCT-008: see below),
  so what is profiled is the benchmark as it is run. Seeds, particles and generations are the
  examples' own (5000 histories x [40 + 120]; LCT-008 4000 x [120 + 250]).
- **Machine.** 4 cores, 16 GB, Linux 6.18 (Firecracker VM), 2026-09-27,
  commit `485ffec74` for the baseline.
- **Classification.** A stack is *transport* if it contains a transport frame
  (`run_keff`, `run_keff_csg`, `transport_history`), otherwise *data prep* if
  it contains any `njoy_outram_park_fork` frame or `Nuclide::from_tape`. The
  test is on the whole stack, because rayon worker threads do not carry the
  caller's frames.
- **LCT-008 is profiled with `--cheap-nuclides`** (fuel, moderator,
  soluble boron and the Al/Si/Mn clad), by maintainer direction on
  2026-09-27. Its default tape set cannot finish on this machine (Finding 3),
  and the script defaults to the cheap tier for that reason. The one run of
  the default set is kept only as the record of where it fails.
- **Reproduce:** `scripts/profile-icsbep.sh flame|callgrind [out-dir] [case ...]`.

## Finding 1 (fixed): an O(N^2) write-back in RECONR

`rebuild_total_as_sum_of_parts` rebuilds MT=1 as the sum of its partials at
each union-grid energy, then wrote each value back with
`total.pairs.iter_mut().find(..)`: a **linear scan per energy**. On U-235's
~1.2 M-point grid that is on the order of 10^12 comparisons, and it was the
single largest cost in every benchmark: 27-52 % of all CPU.

The fix finds the same pair with a binary search, then applies the original
predicate over a window twice the tolerance wide, so it selects the **same
first match** (`src/reconr/mod.rs`). Verified to change **no output**:

| check | before | after |
|---|---|---|
| `tests/pendf_stages_vs_njoy2016.rs` (8 word-exact PENDF gates) | pass | pass |
| `reconr_mt1_is_the_sum_of_its_parts`, `reconr_u234_unresolved_njoy_golden` | pass | pass |
| U-234 293.6 K ACE vs NJOY2016, whole XSS (449 695 words) | identical | identical |
| U-235 0 K ACE vs NJOY2016, whole XSS (15 616 079 words) | identical, built in 66.0 s | identical, built in **27.7 s** |
| Godiva k, same seed | 1.00074 +- 0.00163 | **1.00074 +- 0.00163** |

Every benchmark, before and after, same seeds, `perf` build:

| case | nuclear data | transport | total | k, before = after |
|---|---|---|---|---|
| Godiva | 245.3 -> **79.8 s** | 33.3 -> 36.4 s | 279 -> **117 s** | 1.00074 +- 0.00163 |
| Jemima | 250.3 -> **80.9 s** | 56.8 -> 60.3 s | 308 -> **142 s** | 0.99953 +- 0.00178 |
| HST-009 | 290.0 -> **97.2 s** | 69.7 -> 66.3 s | 360 -> **164 s** | 0.99779 +- 0.00172 |
| LCT-008 cheap | 286.0 -> **96.2 s** | 98.0 -> 93.6 s | 385 -> **190 s** | 0.99982 +- 0.00123 |

**2.1-2.4x faster end to end, with identical results.** Transport is
unchanged within run-to-run noise on a shared VM, as it should be. In Godiva,
U-238 went 166 -> 33.5 s and U-235 75 -> 43 s.

The full `njoy-outram-park-fork` suite (`scripts/test.sh`, release) passes
with the fix: 1040 passed, 0 failed, 9 ignored.

The quadratic had become worse over time: the RECONR union-grid port
(GitHub #340) made the grids larger. `docs/handoff-heavy-neutronics-runs.md`
recorded 112.1 s for the same three actinides on 2026-09-20; it was 245 s on
2026-09-27 before the fix.

## Finding 2 (open): the transport cross-section lookup

In the multithreaded benchmarks, `ReconrResult::eval_mt` was **35-39 % of all
CPU** before the fix, and is **50-57 %** after it (Jemima 56.7 %, HST-009
50.5 %, LCT-008 51.6 %): it is now the largest single cost in every
benchmark. `Nuclide::base_xs_at_energy`
calls it 7 + N_levels times per evaluation (total, elastic, fission, n2n, n3n,
MT=5 and **every inelastic level**, about 40 for U-238). Each call does a
linear search over the sections and a fresh binary search of a grid of up to
~1.2 M points.

**Callgrind says which half of that matters** (Godiva transport, 500 x
[20 + 5], instruction counts; see "Callgrind" below). Of the lookup's cost,
the **linear search for the section** is the larger part by far:

| inside `eval_mt` (self instructions, % of transport) | |
|---|---|
| `MtReaction` comparison in the section scan (`endf/mt.rs`) | 23.2 % |
| slice iteration of that scan (`non_null.rs`, `iter/macros.rs`) | 34.3 % |
| the energy binary search (`partition_point`, `cmp`) | 15.0 % |
| interpolation and control flow (`reconr/mod.rs`) | 13.9 % |
| bounds checks, hints, `Vec` access | 5.6 % |
| **`eval_mt`, inclusive** | **91.9 %** |

So the cheapest win is to resolve each reaction's section **once per
nuclide**, not once per call: roughly 57 % of transport instructions go away.
A shared energy index (after RECONR every section lives on one union grid)
and a precomputed inelastic sum would take most of the rest; OpenMC does both,
with a lethargy-hashed index and a stored MT=4.

`Material::sample_nuclide` is 76 % of transport: to choose a collision
partner it evaluates every nuclide's full cross-section set, inelastic levels
included, where only the totals are needed.

Not changed here. It is a data-structure change in `outram-mc-libs`, and the
transport path deserves its own paired measurement.

## Finding 3 (open, GitHub #339): Fe-57 makes LCT-008's default run impossible on 16 GB

Since 2026-09-20 LCT-008 loads every nuclide its material cards name,
including Fe-57 (ENDF/B-VIII.0 LRF=7). On this machine, reconstruction of
Fe-57 **ran out of memory** after ~20 CPU-minutes: a 1.48 GB allocation
failed under a 14 GB address-space cap. So the default LCT-008 cannot finish
here, and the timing rows above are for `--cheap-nuclides`.

The partial profile shows where Fe-57 spends its time:
- 71 % in the LRF=7 path: `reconr::rml::add_rml_range` ->
  `refine_resonance_grid` (rayon) -> `samm` cross sections;
- inside it, **~32 % of all CPU is malloc/calloc/free**, allocated per energy
  point: `PackedComplexMatrix::zeros`, `setr`, `setxqx`, `yfour`,
  `cross_sections`, and dropping `SetrOutput`.

Hoisting those buffers out of the per-point loop would remove most of that.
Whether it also removes the out-of-memory is **not established**. The failing
allocation is large and single, which points at a collected vector rather
than at per-point churn.

## Smaller items

- **Godiva's transport is single-threaded.** `KeffSettings::default()` has
  `compute: CpuSingleThread` and `godiva_keff_endf_local` does not override
  it; the other three pass `CpuMultiThread`. Not changed, because the
  example's reproduction gate compares against a recorded seeded result.
- **`through_pendf_text` is 8.7 % of Godiva after the fix.** It rounds every
  value through NJOY's 11-column text format, which is required for word
  parity with NJOY, but it is done by formatting and parsing strings.

## Callgrind (transport only)

Instructions collected in transport at 500 x [20 + 5], and the share of them
in each function (inclusive):

| | Godiva | Jemima | HST-009 | LCT-008 cheap |
|---|---|---|---|---|
| transport instructions | 4.0e9 | 2.88e10 | 3.34e10 | 2.38e10 |
| `Nuclide::base_xs_at_energy` | 93.0 % | 94.7 % | 86.5 % | 72.8 % |
| `ReconrResult::eval_mt` | **91.9 %** | **91.6 %** | **80.7 %** | **71.8 %** |
| `Material::sample_nuclide` | 76.4 % | 81.9 % | 77.8 % | 65.2 % |
| geometry (`locate`, `distance`) | - | 1.1 % | 5.2 % | **17.1 %** |
| S(a,b) sampling and lookup | - | - | 1.3-2.6 % | - |
| URR probability-table sampling | - | 3.3 % | - | - |

It agrees with the sampling profiles and sharpens them. **Cross-section
lookup is 72-92 % of every instruction a history executes.** Geometry matters
only in the LCT-008 lattice, where it is the second cost at 17 %. Everything
physical (collision kinematics, secondary sampling, nu-bar) is a few percent.
Per-case summaries: `icsbep_2026_09_27/callgrind_<case>.txt`.

A first attempt at 500 x [2 + 3] collected **nothing**: transport took 0.6 s
under valgrind and was over before a 2-second poll switched instrumentation
on. The script now polls every 0.1 s, runs 25 generations, and refuses to
report a profile whose instruction total is zero.

## What to do next, in order of measured payoff

1. **Resolve each reaction's section once per nuclide** (Finding 2). This is
   ~57 % of transport instructions in Godiva and a small, local change.
2. **Share one energy index across a nuclide's sections**, and precompute the
   inelastic sum. That takes most of what is left of the lookup.
3. **Fe-57 / LRF=7 memory and allocation** (Finding 3, GitHub #339), so
   LCT-008's default configuration can run on a 16 GB machine at all.
4. Resonance evaluation (RM) and BROADR are now the largest data-prep costs:
   13-21 % and 10-13 % of CPU in the three multithreaded benchmarks, and
   43.5 % and 27.8 % in Godiva, whose transport is single-threaded and so
   weighs less. That is real physics work, parallelised, with no obvious
   waste in the profile.
