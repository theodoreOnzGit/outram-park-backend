# Lesson philosophy

How every OUTRAM PARK tutorial and deep dive is built. Set by the maintainer
in the design sessions of 2026-10-04. The worked examples are the Monte Carlo
rungs (#520: Godiva #521, uranium in graphite #524, lumping #525, LCT-008
#526, TRISO and HTR-10 #528).

This document says **why and in what shape**. The file and anchor conventions
are in #510. The mobile layout is a hard rule in
[`docs/claude-md/mobile-first-tutorials-and-demos.md`](../claude-md/mobile-first-tutorials-and-demos.md).

> **Research, education and V&V only.** Every lesson carries this banner from
> `RESPONSIBLE_USE.md`, and no lesson frames its results as authoritative for
> operation, licensing, safety or emergency response.

---

## 1. Curiosity first: open on a demo, not a definition

A reader arrives at something moving that makes them ask *"what is this?"*.
For Monte Carlo that is the TRISO pebble demo: neutrons flying through fuel.
The lesson exists to answer the questions the demo raises, in the order the
reader would ask them.

The track ends back at the same demo. By then the reader can explain every
part of it.

## 2. A lesson is a chain of questions

Each answer contains the thing that raises the next question:

```
demo → "what is this?" → Monte Carlo simulates neutrons
     → "how?" → free-path sampling, d = -ln(xi)/Sigma_t
     → "what is Sigma_t?" → N times sigma  ──(side path)──→ nuclear data track
     → "a collision happened, then what?" → pick the reaction
     → "how do we pick?" → random numbers  ──(side path)──→ the LCG in petir
     → …
```

- **Every step has the same anatomy:**
  1. the question;
  2. the shortest answer;
  3. the formula, with explanation;
  4. an animation of exactly that idea;
  5. the code walk down to the function that does it;
  6. the measured check, where there is one;
  7. a **predict** prompt that sets up the next question.
- **Side questions are links to other tracks, not detours.** "Where do cross
  sections come from?" opens the nuclear data track. The main lesson keeps
  moving.
- **Predict before you show.** Before each animation or result the reader
  commits to a guess: denser fuel, further or shorter flights? Heavy or light
  nucleus to slow a neutron? A prediction that turns out wrong is the point.
- **Use, then modify, then create.** Every lesson ends with a real example to
  run, a parameter to change, and a small thing to build. For Godiva: run it,
  change the radius, find the critical radius.

## 3. Start analog and simple, then add one piece of physics per rung

- **Analog Monte Carlo first.** Each neutron is followed exactly as nature
  would: no weights, and tallies are plain counting. Estimators, variance
  reduction and other cleverness come later, each when a problem needs it.
- **Each lesson is one rung of a ladder.** A rung adds one piece of physics,
  and the problem that physics creates motivates the next concept:

  | Rung | System | What it adds |
  |---|---|---|
  | 1 | Godiva, a bare sphere | free flights, collisions, surface tracking, leakage, fission generations, k; leakage and "all fission is fast" by counting |
  | 2 | uranium mixed into graphite | slowing down, lethargy, free gas and S(alpha,beta), resonance escape, the four-factor formula, and why the homogeneous mixture fails |
  | 3 | lumped uranium in graphite | spatial self-shielding, and why the 1942 pile used lumps |
  | 4 | LCT-008, a water-moderated rod lattice | hydrogen moderation, lattices, the light-water reactor |
  | 5 | TRISO, then the HTR-10 pebble bed | double heterogeneity, delta tracking, shortcuts and what they cost |

- **The simplest system first, even when history did otherwise.** Rung 2 mixes
  the uranium evenly through the graphite because that is simpler, then shows
  why nobody built it that way. The lumped version is the next rung.
- **Statistics enters when a problem needs it.** An error bar appears with its
  first result and one line of meaning ("why it can be trusted comes later").
  The full treatment (the central limit theorem and its failures, correlated
  cycles, variance reduction) arrives where things first get slow or
  misleading.
- **Each rung ends on a check that can fail.** That is a measured experiment
  where one exists (Godiva, LCT-008), and otherwise an analytic solution, a
  deterministic solution, or another code.

## 4. Code walks are central

Showing the leaf function is not enough. Every code step shows **how the code
gets there**: the entry point calls this function, which calls this one, all
the way down to the lines that match the concept. The lessons double as the
documentation of the code's architecture.

- **Generated by a tool, gaps filled by hand.** `kovan-cli code-walk` (#523;
  ~~`kopitiam callees` until it lands~~ **landed 2026-10-04**; see
  `crates/kovan/README.md`, "code-walk") asks rust-analyzer for the real call
  chain. A hop it cannot resolve (a trait method, a closure, a parallel
  iterator, a macro) is filled in by reading the source and **labelled
  "filled by hand"**.
- **Kept in marked blocks** (`<!-- code-walk: from=<file>::<fn> to=<file>::<fn> -->`),
  so CI can regenerate them and fail when a function moves or a chain breaks.
- **Every hop links to its exact lines** at the commit the site was built
  from.
- **Every hop shows its code on the page** (maintainer direction,
  2026-10-05: "I don't want to have to click to see code snippets"). The
  generator puts each hop's lines inline, pulled from the source by mdBook
  `{{#include}}`: the whole concept function, and the signature and call site
  of each function on the way to it. A link alone is not a code walk.
- **Code shown inline is pulled from the source at build time**, never copied
  by hand.
- **Each lesson ends with an exhaustive call tree**: everything its entry
  point reaches inside the workspace, as an architecture map.
- **Say when there is no function.** Lethargy gain and resonance escape are
  not computed anywhere; they *emerge* from repeating one collision. Saying so
  teaches where the physics actually lives.
- **Show the forks.** When the code takes different branches by regime (S(alpha,beta)
  below its cutoff, free gas below 400 kT, target at rest above), the walk
  shows every branch, and the animation labels which one handled each
  collision.

## 5. Honest numbers

The workspace rule "get the process right first" applies to every number a
lesson shows.

- **Quote as recorded:** with file, date and commit. Never retype a number
  from memory.
- **Use the latest record, and say which number to quote.** When several
  exist (one seed against a pooled ensemble, an old tier against the current
  one), name the one that counts and why.
- **Re-measure before quoting** any record older than a change that could
  move it (for example the 2026-09-20 physics defaults or the 2026-09-30
  OpenMC-parity audit). Superseded numbers are struck through, never silently
  replaced.
- **Show the misses.** A result 2 sigma or 6 sigma from its reference is
  shown as it is, with what is known about why.
- **History of a number is a dated box, never the current result.** "How the
  code got here, August 2026" may show each piece of physics moving k. It is
  labelled as history.
- **Name the data and the method.** ENDF/B-VIII.0 read directly through the
  workspace's own NJOY port is the default. Faster data paths (such as WMP)
  arrive at the rung where the problem they solve appears, not before.
- **Verification is not validation.** Against an analytic solution, a
  deterministic solver or another code, the page says *verification*. Only a
  measured experiment is *validation*.
- **State the deliberate liberties.** Every model simplification (a lattice
  where the reactor was random, whole pebbles only, an assumed pressure, a
  dropped trace nuclide) is listed with why it was taken and what it may
  cost. If its effect has not been measured, say so rather than estimate it.
- **Write the prediction before running.** When a lesson needs a new
  calculation (such as k-infinity against the carbon-to-uranium ratio), the
  expected outcome is written down first, and the page reports what the run
  gave, including when it contradicts the expectation.

## 6. History, sourced

History is the hook where it helps: the 1942 pile, naval reactors, Untermyer
and BORAX, Shippingport.

- **Every historical claim cites a source with its page**, and open-corpus
  sources get a verbatim quote.
- **The maintainer supplies the literature.** Agents may identify candidate
  open sources and list them on the issue. They do not ingest literature or
  write unsourced history; a claim waiting for a source is a visible
  placeholder.

## 7. The user experience

- **Mobile-first is a hard rule.** The main view fills the page, with
  on-screen zoom in, zoom out and Reset. Every control sits in a collapsible
  side panel, folded on narrow screens. Gestures supplement the buttons, never
  replace them. Every page is checked at phone width before it counts as
  done.
- **No lagging is a hard rule.** The app never freezes. All computation runs
  in a background worker or thread and streams results, with progress shown,
  while the view stays responsive to panning, zooming and sliders.
- **One demo per track, with a rung setting**, not one demo per lesson. Each
  rung has a stable short name (`?rung=godiva`) and its own modes, e.g. Godiva
  *Watch* (illustrative) and *Run k_eff* (a real single-threaded run with a
  live `openmc.run()`-style console).
- **Each rung links to its own page, both ways.** The lesson opens the demo at
  its rung. The demo's "What's happening here?" opens that rung's page. One
  table drives both directions, and CI checks it.
- **Animate the physics truthfully.** A neutron's displayed speed follows the
  classical kinetic energy, v proportional to the square root of E, so slowing
  down is *visible*. The slider reads "speed at 1 eV" everywhere. Its default
  follows the rung's spectrum: 7 cm/s at 1 eV for thermal systems, 7 cm/s at
  1 MeV for fast ones. Finished paths are cleared, not left as clutter.
- **Link the views.** Where it teaches, the geometry is shown beside the
  physics it obeys. For example, the zig-zagging neutron sits next to the
  log–log cross-section graph, with a marker riding down through the
  resonance peaks; a capture removes the neutron in both views at once.
- **Lesson, code and literature side by side**, with review stamps and a
  "doesn't tally" button on every page (#509, #510, #511). A page the code
  contradicts is a defect, fixed in the same change.

## Checklist for a new lesson

- [ ] Opens on a demo and a problem; ends back at the demo or at the next rung.
- [ ] Every step: question → answer → formula → animation → code walk → check → predict.
- [ ] Adds one piece of physics over the previous rung; analog before clever.
- [ ] Code walks generated by the tool, hand-filled hops labelled, exhaustive tree appended.
- [ ] Every number quoted from a record (file, date, commit), re-measured where stale, misses shown.
- [ ] Verification and validation named correctly; deliberate liberties listed.
- [ ] History cited with source and page, or left as a visible placeholder.
- [ ] Demo rung linked both ways; truthful animation speed; checked at phone width; stays responsive while computing (no lagging).
- [ ] Education-only banner; review stamp; "doesn't tally" button.
