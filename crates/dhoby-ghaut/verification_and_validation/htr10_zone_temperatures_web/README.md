## What changed on the page

**HTR-10 → "Whole core" → "Zone temperatures" panel:**
- Eight sliders, 20–1800 °C in ~~5 °C~~ 1 °C steps (**CORRECTED 2026-11-03**: with 5 °C steps counted from 20 °C, the record's 27 °C was off the grid and the slider showed and snapped it to 25 °C):
  - fuel pebbles, moderator pebbles, helium coolant;
  - top, side and bottom reflector;
  - control rods, boronated bricks.
- "Same for all zones", and "Reset" to the record's 27 °C.
- A red warning naming every zone above 1600 °C (the TRISO limit).
- **Apply** restarts the worker pool at the new temperatures:
  - each zone's nuclides are reprocessed at its temperature (RECONR, BROADR, HEATR, PURR) and its thermal laws generated by LEAPR;
  - every (nuclide, temperature) already in this browser's IndexedDB loads from there;
  - the sliders and Apply are locked while a run or sweep is going.
- `?temps=all:300,fuel:900,coolant:500` (°C) sets the temperatures from a link.

**Worker messages:** "process" and "assemble" carry the eight temperatures; the jobs are `ParametricStudy::plan`'s at those temperatures.

**Corrected on the page:**
- The recorded tracks the view opens on were baked from the record's model (27 °C, graphite and SiC laws from the tapes). The page said "the same model"; it now says which model.
- The record lines on the k plot are marked as not a reference once the temperatures are not 27 °C everywhere.

## Methodology

- **Build:** `crates/dhoby-ghaut/web/monte_carlo/build.sh` (release wasm, wasm-bindgen 0.2.129), served by `python3 -m http.server`.
  - 274.7 MB of tapes, 38.6 MB downloaded.
- **Machine:** cloud container, 4 vCPU Intel Xeon (model not exposed), 15 GiB. Chromium 141 headless, **software rendering**. Frame and probe times are therefore far slower than on a real device.
- **Screenshots:** `web/shots_temps.js`, 390 × 844 (touch) and 1280 × 900, at `?temps=all:300,fuel:1650,coolant:500`, panel scrolled to the sliders.
- **Data, time, memory, no lag:** `../nuclear_data_cache_web/run_headless_932.mjs`. The browser runs through a `--no-sandbox` wrapper: the container runs as root. It drives `?rung=htr10&mode=watch&view=core&autostart=1&temps=all:300,fuel:900,coolant:500&particles=200&inactive=1&active=2`. It records:
  - every console line, including each worker's "assembled" line with its wasm memory;
  - long tasks and frame gaps;
  - a wheel probe every 2 s;
  - at the end, every IndexedDB record with its SHA-256 recomputed in the page.
- **Cache reuse:** the same harness twice on one browser profile. First the setting above, then the same with only the coolant changed to 600 °C.
- **Pass criteria:**
  - every product stored = recomputed;
  - the run completes;
  - memory per worker well under the 4 GiB wasm32 limit;
  - the second load reprocesses only the coolant's helium and reads everything else from the cache.

## Results

**Screenshots** (`shots/`): phone `temps_phone_390x844_1.png`, desktop `temps_desktop_1280x900_1.png`.
- All eight sliders, the "same for all" box, Reset, the red TRISO warning naming "Fuel pebbles", and the note that the core is built at these temperatures, all legible and reachable at 390 px with the panel open.
- Desktop: the same, beside the core and the views.

**Non-uniform load** (fuel 900 °C, coolant 500 °C, the rest 300 °C), fresh profile:

| quantity | result |
|---|---|
| jobs (nuclide or law, temperature) | 44 (36 at one temperature) |
| data ready | **411 s** on 3 workers |
| U-235 / U-238 at 900 °C made in | 227.9 s / 188.0 s |
| wasm memory per worker after assembly | **511 / 359 / 359 MB** (4 GiB limit) |
| assembly per worker | about 21 s (majorant 14 s, nuclides 6 s, geometry 0.6 s) |
| IndexedDB records | 44, stored = recomputed for all 44 |
| run | 3 generations on 3 workers, finished (k is 200 × [1 + 2], not a result) |
| main-thread probe (wheel → title) | median 192 ms, 95th percentile 286 ms, max 631 ms (191 probes) |
| frame gaps | max 217 ms; 33 of 7 526 frames over 100 ms |

**Interpretation:**
- **Memory and correctness:** the per-zone data fit easily: about 0.5 GB per worker against the 4 GiB a wasm32 worker can address. Every product the browser saved is the product it made.
- **Responsiveness:** the page stays responsive while processing and assembling, within this harness's software-rendering frame times. The 2026-10-26 lag check of the same tab on the same kind of machine had a 133 ms median frame while processing, measured with a different instrument (frame interval). The probe here is wheel-to-title, so the two medians are not directly comparable.

**Cache reuse**, two loads on one browser profile:

| load | temperatures | nuclear data | data ready | memory per worker |
|---|---|---|---|---|
| A | fuel 900, coolant 500, rest 300 °C | all 44 processed now | 416 s | 511 / 359 / 359 MB |
| B | fuel 900, **coolant 600**, rest 300 °C | **42 from this browser's cache, 2 processed now** (He-3, He-4 at 873.15 K, 0.1 s each) | **24 s** | 359 MB each |

- Both loads stored = recomputed for every record (44, then 46).
- So moving one slider reprocesses only that zone's nuclides. Everything else is read back from IndexedDB, and what remains is the assembly (about 21 s per worker, 14 s of it the bed majorant).
