## What is being predicted

The `htr10` rung of the Monte Carlo web demo loading the **whole** HTR-10
model the recorded runs used (`nee_soon::htr10_rmc::assemble_explicit_triso`,
14 rings, N = 12 layers; `Htr10DataConfig::default()`: ENDF/B-VIII.0 at
300.15 K and tolerance 1e-3, URR and DBRC on, natural carbon, helium, real
Ni/Fe rod steel, every bound thermal law, the two UO₂ laws generated by
LEAPR), with the data processing split by nuclide over a pool of Web Workers:
each nuclide's RECONR + BROADR + PURR (and each thermal law) runs in one
worker and is shipped as numbers to the others, which rebuild the rest of the
nuclide from the tape (`Nuclide::process_evaluation` /
`Nuclide::from_processed`, pinned bit for bit by
`outram-mc-libs/tests/processed_evaluation_round_trip.rs`).

## Prior numbers this rests on (all quoted, none measured here)

- Native data processing for the whole core, one thread: **92–131 s** on the
  i9-13900K (2026-10-01 record) and **108–336 s** on a loaded Xeon W-2195
  (2026-10-07 record, `htr10_seker_2026_10_07_10k/RUN_PARAMETERS.md`); the
  N = 12 log there itemises U-235 88.4 s, U-238 54.2 s, the two LEAPR laws
  13.0 + 20.3 s, everything else under 4 s each.
- Browser against native on the same data path: **1.7–2.1×** (the fuel-zone
  k∞ on #528: 283 s browser against 135–165 s native, 2 shared cores of a
  2.1 GHz Xeon).
- Native transport of the core: **8.5–14.8 ms of CPU per history** (i9,
  2026-10-01 record); peak RSS of a whole native run **≤ 0.68 GB** with 7
  threads (2026-10-07 record).
- Recorded k at N = 12 (VIII.0, 10 000 × [5 + 135], 2026-10-07):
  **0.995125 ± 0.001055**; RMC at the equal-ball-count height **0.999419**.

## Predictions

Hardware for the measurement: this desktop (i9-13900K), headless Chromium,
the browser held to 5 logical CPUs, the machine shared with other agents.

| quantity | prediction |
|---|---|
| P1. Data, the whole core, **one** worker | **3–6 min** (native 92–131 s × 1.7–2.5) |
| P2. Data with a pool of **4** workers | **1.5–3 min**: the critical path is U-235's processing (~45 s native on this machine, × 1.7–2.1) plus each worker's own pass rebuilding all ~~41~~ 38 slots (count corrected 2026-10-07 before any measurement; the predicted range is unchanged) from the tapes (I expect 10–25 % of the one-worker time) plus the majorant |
| P3. Wasm memory per worker once ready | **250–600 MB**; the page itself under ~300 MB while products are relayed |
| P4. Transport per history per worker | **13–35 ms** (native 8.5–14.8 ms × 1.3–2.5) |
| P5. A **1000 × [5 + 20]** k run on 4 workers | **80–220 s**, i.e. 3–9 s per generation |
| P6. Its result at N = 12 | σ ≈ **800–1000 pcm** (the record's 105 pcm × √(1.35 M / 20 000) ≈ 860 pcm), mean within 2σ of the record's 0.995125, so **0.978–1.012** |
| P7. Same run on 1 worker and on 4 | **identical bit for bit** (the per-history streams and the history-order reduction of `transport_csg::distributed`, pinned against `run_keff_csg_par` by its own tests) |
| P8. Browser against native, same settings and seed | **not** bit-identical: the wasm build uses Rust's libm where native uses the platform's, so histories drift apart after the first transcendental that rounds differently; agreement within statistics only |
| P9. Main-thread long tasks (> 50 ms) | a few during the relay of the largest products (U-235, U-238: tens of MB each), none during transport |
| P10. Phone (390 px, `deviceMemory` ≤ 4) | 1–2 workers by the sizing rule; data **6–15 min** on a real phone CPU (2–3× slower than this desktop per core); live is opt-in there, the recorded tracks play first |

**Decision rule, fixed now:** live data and live tracks if P2 comes in under
~5 min on the desktop with progress shown, otherwise baked tracks only; a
live k_eff if P5 comes in under ~5 min.

## Addendum, 2026-10-08: the DEM random bed in the live k (written before it was built or measured)

Maintainer-approved (#787, 2026-10-08): the same live low-statistics k on
the DEM random bed (#216's pour at µ = 0.1, cut to the lattice's 16 681 core
pebbles, `assemble_explicit_triso_from_centres`, the paper's 57:43 fuel
split). Prior numbers, quoted: the DEM-bed smoke run (2026-10-05, 500 ×
[10 + 20], 12 threads of the i9-13900K) took 38.3 s for 15 000 histories,
about **31 ms of CPU per history**, against 11–15 ms for the lattice natively
here (`logs/bake_native.log`) and **12–19 ms per history per worker** in the
browser (README). The DEM core has 88 693 cells against the lattice's
43 445, and assembles in 0.2 s natively.

| quantity | prediction |
|---|---|
| D1. Browser transport per history per worker, DEM bed | **25–50 ms** (the native ratio, 2–2.5×, on the browser's lattice cost) |
| D2. A 1000 × [5 + 20] run on 3 workers (4 cores in all, page included) | **4–7 min** (9–17 s per generation) |
| D3. Rebuilding the core as the DEM bed in a worker | **0.3–1.5 s** |
| D4. Extra wasm memory per worker over the lattice core | **20–80 MB** |
| D5. Page long tasks over 100 ms during the DEM run | **none** on a quiet machine (the page keeps one of the 4 cores) |
| D6. Its k | within 2σ of the lattice live run (σ ≈ 1000 pcm each): **the demo cannot resolve a lattice-against-random difference**, and the page must say so |

No native random-bed k is assumed: another agent's 10 000 × [5 + 135] run is
in progress, and the page leaves a marked slot for it.
