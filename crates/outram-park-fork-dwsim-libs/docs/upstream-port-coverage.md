## 1. Buckets, and the evidence bar for each

| Bucket | Meaning used here |
|---|---|
| `PORTED + VALIDATED` | Present in Rust **and** backed by a test that compares against an analytical result, a published value, or a cross-code run, with the number and the reference cited. Passing unit tests are *not* enough. |
| `PORTED + NEEDS DOGFOOD` | Present in Rust, tests exist, but no validation evidence at the bar above. This is the default for AI-assisted ports per `RESPONSIBLE_USE.md`. |
| `PARTIAL` | Present in Rust but a material part of the upstream behaviour is absent or non-functional, with the gap stated. |
| `MISSING + REQUIRED` | Absent, and its absence blocks the refinery programme's crude-estimate infrastructure target. Each such row has a paragraph in §9. |
| `MISSING + NOT CURRENTLY REQUIRED` | Absent, no current blocker. |
| `DO NOT PORT` | Out of scope by the issue's own rules (UI, CAPE-OPEN, .NET architecture, external bridges that another workspace crate already covers). |

**On `PORTED + VALIDATED`.** No row in this matrix lands there. The crate's own README, `thermo/mod.rs`, `columns/mod.rs`, `reactors/mod.rs`, and `separator/mod.rs` each state "verified, not benchmark-validated" / "no human V&V", and `verification_and_validation/README.md` contains the convention but **no V&V records**. The tests that come closest — `thermo/prsv2_full.rs:517-544` (ethylene vapour pressure at `Tb = 184.55 K` vs Poling et al. and NIST Antoine), `thermo/transport.rs:630-645` (methane/nitrogen viscosity vs NIST), `thermo/seawater.rs:619` (density vs Sharqawy 2010), `thermo/lkp.rs:584-588` (second-virial limit vs the Pitzer/Prausnitz correlation) — are single pure-component spot checks that pin a *port* to a *reference point*; they are not validation of the mixture models the refinery programme will use, and none has a human-reviewed V&V record. Calling any of them validated would be the overclaim the issue prohibits. They are listed as `PORTED + NEEDS DOGFOOD` with the spot check noted.

## 6. The `Z <= B` question — what upstream does, what the port does

The issue asks for particular attention here because the workspace already shipped a defect where `select_root` accepted `Z <= B`, `ln_phi` evaluated `ln(Z − B)` on a non-positive argument, and callers received `Some(NaN)` instead of `None`.

### 6.1 The port today (audited at `e9548cef`; last two bullets amended at `9cc24a6e`)

- **`thermo/cubic_eos.rs:556-585` — `select_root(roots, phase, b)`.** Every candidate must satisfy `r.is_finite() && r > b` (`:564`); the liquid branch additionally requires `r > 0.0` (`:576`). Vapour takes the largest admissible root, liquid the smallest. The comment block at `:557-563` records the rationale (`v = ZRT/p` must exceed the covolume; the cubic "still *has* roots below `B` — spurious ones that appear once the fluid is far above its critical temperature"). So the defect the issue describes is **fixed at this commit**.
- **Propagation.** `z_factor` (`:359-374`), `z_vapor`/`z_liquid` (`:378-387`), `ln_phi` (`:407-436`, `?` at `:426`) and the departure routine (`:530-551`, `?` at `:542`) all return `Option` and propagate `None`. `ln_phi`'s doc (`:399-405`) states the contract: "Returns `None` if the phase has no admissible `Z` root … Every returned value is finite."
- **Derived EOS modules inherit the guard.** `pr1978.rs:208-212` and `prsv2_full.rs:266-270` obtain `zf` through `CubicEos::z_vapor` / `z_liquid` and only then evaluate `-(zf - b).ln()` (`pr1978.rs:220`, `prsv2_full.rs:278`). `eos_variants.rs:461` goes through `z_factor`.
- **Callers fall back rather than propagate NaN.** `thermo/property_package.rs:186-212`: if either phase's `ln_phi` is `None`, or any resulting `K` is non-finite or non-positive, the package returns Wilson-correlation K-values ("Belt and braces over `ln_phi`'s own `Z > B` guard", `:198`). `columns/thermo_bridge.rs:231, :252, :340, :366` filter non-finite K and departure values the same way, matching upstream's own `AUX_PVAPi / P` fallback (`BubblePoint.vb:1133`, `SumRates.vb:217`, cited at `thermo_bridge.rs:16`).
- **One unguarded cubic remains, and it is safe by argument, not by guard.** `thermo/chao_seader_grayson.rs:480-505` solves its own Redlich-Kwong cubic and takes the *largest* real root without filtering (`:492`), then evaluates `-(zv - big_b).ln()` (`:497`). For the RK form `Z³ − Z² + (A − B − B²)Z − AB = 0` the residual at `Z = B` is `−2B² < 0` and the cubic is positive as `Z → ∞`, so a real root strictly above `B` always exists and the largest root is always admissible. (The same algebra gives `−2B²` for the PR form, which is why the spurious-root problem is a *liquid*-root problem: it is the smallest positive root that can fall below `B`.) This reasoning is not written down in that file and is not pinned by a test.
- **The guard is now pinned by a test — amended 2026-09-11 (`9cc24a6e`).** The audit found no such test; one exists now. `cubic_eos.rs:886`, `select_root_rejects_a_root_at_or_below_the_covolume`, constructs `A = 0.05, B = 0.10`. Because the PR cubic satisfies `f(B) = -2B² < 0` always and `f(0) = B(B + B² - A) > 0` whenever `A < B + B²`, a spurious sub-covolume root is *guaranteed* to exist for that pair rather than being an accident of a particular fluid, and the test asserts it is in the root set before asserting that neither `z_vapor` nor `z_liquid` returns it and that `ln(Z - B)` is finite on whatever they do return. Verified passing in release on 2026-09-11 as part of the 696-test lib suite.
- **Two narrower properties remain unpinned.** (a) The `None` *branch* of `select_root` is still not exercised: in the constructed case one root (`Z ≈ 1.16869`) clears the covolume, so `select_root` returns `Some` for both phases. (b) No test in `property_package.rs` asserts the Wilson-K fallback on a request where `ln_phi` returns `None`. The residual claim "no `Some(NaN)` ever escapes `ln_phi`" is therefore now protected by a test for the *covolume rejection* and still only by review for the *empty-root-set* path. Narrowed follow-up in §9.7.

### 6.2 Upstream at `1abf72d1`

Upstream has **no `Z > B` check anywhere** in the PR / SRK / PR78 model files (grep over `Models/PengRobinson.vb`, `Models/SoaveRedlichKwong.vb`, `Models/PengRobinson78.vb`, `PropertyPackage.vb`, `BaseFlashAlgorithm.vb` for `Z < B`, `Z <= B`, `Z - B <`, `< BG`: zero hits). What it does have:

1. **Root solver.** `DWSIM.Math/CubicRoots.vb:26-30` — `Poly_Roots` is a thin wrapper over `CalcRoots` (`:119-175`), a Newton iteration launched from three fixed seeds (`r = 0.01`, `0.99999999`, …) with a `cnt >= 1000` failure flag returned as an "imaginary" marker in column 1. It is not a closed-form Cardano solve; the Rust `real_cubic_roots` (`cubic_eos.rs:594`) is. The two were **not** compared numerically in this audit.
2. **`Z_PR` (`Models/PengRobinson.vb:212-350`, and `Z_SRK` `SoaveRedlichKwong.vb:92-230`).** Sorts the three roots ascending and returns `temp1(0,0)` (smallest) for `TIPO = "L"` and `temp1(2,0)` (largest) for `"V"` — **no positivity check and no covolume check** (`:337-343`). This is the routine the Rust `z_factor` doc cites (`cubic_eos.rs:356`), and the Rust port is stricter than it.
3. **`CalcZ2` (`Models/PengRobinson.vb:1610-1669`).** Keeps only roots that are real (`temp1(i,1) = 0`) **and positive** (`temp1(i,0) > 0`, `:1659-1661`), and **throws** `"PR EOS: Unable to calculate compressibility factor at given conditions."` if none survive (`:1663-1665`). This is the `Z > 0` guard — weaker than `Z > B`.
4. **The fugacity path flashes actually use — `CalcLnFugCPU` (`:1246-1262`), SRK equivalent (`SoaveRedlichKwong.vb:369-386`).** Takes `CalcZ2`'s list; throws a user-facing exception if it is empty (`:1248-1253`, "This error occurs when the PR EOS is unable to find a density root…"); `phase = 0` → `_zarray.Min`, `phase = 1` → `_zarray.Max`, otherwise `ZtoMinG` picks the root of **minimum Gibbs energy** (`:1258-1261`). So for a liquid request upstream returns the smallest *positive* root even when that root is `<= B`, and `Math.Log(Z - BG)` then yields `NaN` in .NET exactly as `ln` does in Rust — the difference is that upstream's exception fires only when *no* positive root exists.
5. **The H/S departure path (`:700-771`, SRK `:584-639`).** Same sort-and-pick with two extra heuristics: `If Z < 0 Then Z = temp1(1, 0)` (middle root, `:752`) and, if `Poly_Roots` reports failure, a Newton restart from `Z = 1` (vapour) or `0.05` (liquid) with `If Z < 0 Then Z = 1`, looping `Until Math.Abs(findZV) < 0.0001 Or Double.IsNaN(Z)` (`:762-771`) — i.e. a `NaN` `Z` *terminates* the loop and is used.
6. **Elsewhere.** A brute-force `Z` sweep throws `PropPack_ZError` when `Z < 0` (`:1887, :2047, :2219, :2391`); `If Z < 0.0# Then Z = -Z` (`:2594`); and `If Z < 0.302 Then phase = "L" Else phase = "V"` (`:1754`) is the phase-identification heuristic.

**Conclusion.** Upstream guards `Z > 0` and "no real positive root" (exception), never `Z > B`; the spurious sub-covolume liquid root is not filtered upstream and would produce `NaN` in `Math.Log(Z − B)` there too. The Rust port's `select_root` is therefore **stricter than the reference**, and its `None` → Wilson-K fallback in `property_package.rs` is a port design decision with no upstream counterpart (upstream throws). Two things the port does *not* carry from upstream: the minimum-Gibbs root choice (`ZtoMinG`) when the caller does not name a phase (the Rust API always takes a `Phase`), and the Newton-restart heuristics of item 5. Neither is a defect; both are documented differences. Whether `ZtoMinG` itself would select a `Z <= B` root (its `G` evaluation would be `NaN`, and .NET's ordering of `NaN` in the min search was not checked) is **unverified**.

## 9. `MISSING + REQUIRED` — what each gap blocks (proposed follow-ups, not filed)

Per the issue, these are the rows that generate work. **No GitHub issues were opened and no beads were filed by this audit**; the orchestrator decides. Ordering is by how much else each one unblocks.

### 9.1 Material-stream property calculation (F2)

*What is missing.* The upstream `MaterialStream.Calculate` → `DW_CalcEquilibrium(spec1, spec2)` → phase-property fill. The port's solver marks a stream "calculated" after snapshotting its inputs and leaves whatever phase split was already stored (`flowsheet_solver/evaluator.rs:52-61`).

*What it blocks.* Every physics-bearing flowsheet run. A heater that sets an outlet enthalpy, a valve that sets an outlet pressure, a recycle tear stream — each needs the downstream stream re-flashed by its `StreamSpec` before the next unit reads it. Without this, F9/F10's engine can only be exercised on synthetic data, Cavett's Problem stays unsolved (F10), and no imported fixture can be reproduced. It also gates T40 (phase properties) because the natural home for `Cp`/density/etc. is the same fill routine.

*What exists to build on.* `PropertyPackageModel::flash_pt` (`property_package.rs:241`), `energy_flash::{flash_ph, flash_ps}`, `saturation::{bubble_*, dew_*}`, the nine `StreamSpec` variants already in `streams.rs:221`, and — **added 2026-09-11 (`1314329e`)** — `MaterialStreamData::apply_vle_flash` (`streams.rs:1027`), the write-back half: given a converged `(β, x, y)` it fills the phase slots, so a flash hook is three lines (flash, apply, done). T35 (multicomponent PV/TV) can be left returning an explicit "unsupported spec" error initially.

*What is still genuinely missing, now that the write-back exists.* Three links, of which only the first is small: (a) ~~write a flash answer onto a stream's phase slots~~ — done; (b) `Flowsheet` carries no property package (the importer parses one into `ImportedPropertyPackage::model` and returns it in a side channel the solver never sees — `graph.rs:387-394`, `import/mod.rs:432`); (c) there is no route from a stream's compounds to thermo `Component`s — `StreamCompound` carries only a name and a molar mass, `Component` needs `Tc`/`Pc`/`ω`/`Cp0`, and the crate has no name → `Component` lookup at all, only the hand-entered presets in `component::reference` (F28). Both (b) and (c) change the shape of a public type. The three design options for where a flowsheet gets its thermodynamics are recorded on issue #102; they are not re-argued here.

*A second gap the same size, and the one most likely to be missed — added 2026-09-11 (`9cc24a6e`).* **For petroleum pseudo-components F2 is also a DATA gap, not only a driver gap.** `tests/cut_to_stream.rs` builds a `MaterialStreamData` for each of five crude cuts using public-API output only. All five construct, and their compositions round-trip to 1e-12 — and `MaterialStreamData::validate()` rejects all five, first on `"enthalpy"` and then on `"entropy"`, because a pseudo-component's `ig_entropy_formation_25c` is `NaN` and its Cp0 coefficients are zero **by design**. That test asserts the failure rather than filling entropy from the zeroed coefficients, and is written to fail when the gap closes. Consequence for whoever implements F2: **wiring up the flash alone will land and still not produce a valid crude stream.** Closing it means either supplying ideal-gas entropy/Cp0 for pseudo-components (a characterisation-method question — Lee-Kesler / Riazi-Daubert correlations, T43) or giving `validate()` a documented pseudo-component path. Neither is decided here.
