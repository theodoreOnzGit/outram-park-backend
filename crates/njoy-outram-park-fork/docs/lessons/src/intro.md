This is the **nuclear data track** of OUTRAM PARK: the lessons for
`njoy-outram-park-fork`, a pure-Rust port of the NJOY2016 nuclear-data
processing system (about 124 000 lines of Rust). Every Monte Carlo lesson asks
the same side question sooner or later, *"where does the cross section come
from?"*. This book answers it, one processing step at a time.

**Start here:** [Where does σ(E) come from?](./where-sigma-comes-from.md)

**Live demo:** [the nuclear data demo](../../demos/nuclear-data/?rung=reconr):
real ENDF/B-VIII.0 tapes processed in your browser by this crate, one rung at
a time (RECONR building U-238's σ(E), BROADR's temperature slider, PURR's
bands, THERMR's thermal scattering, a group collapse). It downloads about
11 MB and computes in a background worker, so the page stays live; each rung's
lesson links to it.

## What the crate is

NJOY reads **evaluated nuclear data** (ENDF-6 files: resonance parameters,
tabulated cross sections, angular and energy distributions, thermal scattering
laws, covariances) and turns them into the libraries transport codes read. This
crate is a translation of NJOY2016 version 2016.79 (upstream commit `ac5adf5`)
module by module, kept line-traceable to the Fortran so a disagreement can be
localised to one subroutine.

It is a **derivative work** of NJOY2016, which is under a modified BSD
3-Clause licence (the LANL/DOE variant); the crate is distributed under

[`NOTICE`](https://github.com/theodoreOnzGit/outram-park-backend/blob/@@COMMIT@@/crates/njoy-outram-park-fork/NOTICE).

## The two kinds of page

- **Core rungs** (Part I). One question each, in the order a reader asks them.
  Each rung adds one processing step to the pipeline, and each ends on a check
  that can fail.
- **Extended deep dives** (Part II). Every other public module of the crate:
  output formats for other codes, the OpenMC HDF5 interchange, windowed
  multipole, and the consumer surface the transport crates call. A module that
  is not yet ported is listed as such, not hidden.
- **Coverage** (appendix). One table, module by module: which page teaches it,
  which code walk shows it, and which V&V record supports it. A module without
  a lesson is a visible row.

## How each rung is built

Every rung follows the workspace's lesson format
([`docs/lessons/lesson-philosophy.md`](https://github.com/theodoreOnzGit/outram-park-backend/blob/@@COMMIT@@/docs/lessons/lesson-philosophy.md)):

1. the question;
2. the shortest answer;
3. the formula, explained;
4. the picture (the demo rung, once it exists);
5. the **code walk**, from the entry point down to the lines that do it;
6. the **measured check**, quoted from its record;
7. a **predict** prompt that sets up the next rung.

**Code walks** are generated by `kovan-cli code-walk` from rust-analyzer's
call hierarchy and sit in marked comment blocks in each page's source, which
the site build regenerates and checks (`kovan-cli code-walk-check`): a walk
whose chain breaks or whose functions move fails the build. Hops the tool
cannot resolve (trait methods, function pointers, macros) are marked
`UNRESOLVED` by the tool, and any filled in by reading the source are labelled
**filled by hand**. Each walk is followed by a table, "reading the walk",
saying what every hop does; those tables were first drafted from an earlier
`kopitiam callees` pass (2026-10-04) and their last column says how each hop
was resolved then.

**Code shown inline is pulled from the source file at build time**, never
copied by hand. Code links point at the exact commit this site was built
from, and their line ranges are resolved from the function's name when the
site is built, so a link follows its function when the file changes.

**Numbers** are quoted only as recorded in the repository, with the file, the
date and, where the record gives it, the commit. A record older than a change
that could move it is labelled as such.

**Verification is not validation.** Nearly every check in this book compares
the port with NJOY2016 itself on the same input. That is **verification**: it
shows the translation reproduces the Fortran. It says nothing about whether the
evaluation describes nature; that question belongs to the transport benchmarks
in the Monte Carlo track.

## When something doesn't tally

If a sentence here disagrees with the code it links to, **the page is wrong**
and that is a defect. Please
[open an issue](https://github.com/theodoreOnzGit/outram-park-backend/issues/new)
naming the page and the link. (A structured report form is coming,
[#511](https://github.com/theodoreOnzGit/outram-park-backend/issues/511).)

## The primary source

NJOY2016's manual is open literature: *The NJOY Nuclear Data Processing
System, Version 2016*, R. E. MacFarlane et al., LA-UR-17-20093 (revision of
7 November 2019), BSD-3-Clause-style licence. It is in Kovan's standard
corpus (moved there 2026-10-07) at
`crates/kovan-literature/reactor-literature/kovan-standard-open-corpus/lanl/2022laur1720093.pdf`,
and this book quotes it by section and page.
