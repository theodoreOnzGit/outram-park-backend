# WMP library HDF5 **write** — verified by round trip and by OpenMC reading it

**Date:** 2026-09-24
**Issue:** [gh:#270](https://github.com/theodoreOnzGit/outram-park-backend/issues/270),
scope table row *"WMP library (`WMP_Library`) | read (today) + **write** |
Already partly present."* This was the last row of that table with nothing
behind it.
**Code under test:** `crates/njoy-outram-park-fork/src/wmp/h5_write.rs`
(`WindowedMultipole::write_h5`).
**Tests:** `--test wmp_h5_write_round_trip` (4), `--test wmp_h5_vs_openmc` (2).

## Methodology

`openmc/data/multipole.py`'s `WindowedMultipole.export_to_hdf5` (`/opt/src/openmc`
commit `afa7a14`, MIT) is the specification, **read before writing anything** per
the workspace porting rule — the layout is not inferred as the reader's inverse,
because the reader is more permissive than OpenMC and inverting it would have
produced a file OpenMC cannot use (see below).

Source data is the embedded CORE library (`src/data/wmp_core.wmpl`, MIT CRPG
ENDF/B-VII.1), so neither test needs external data or a network.

Two nuclides throughout, because the **fissionable flag is the one thing the
writer branches on** and a test on one shape would not see the other break:

| nuclide | `data` columns | curve-fit channels | poles | windows | file |
|---|---|---|---|---|---|
| U-238 (fissionable) | 4 | 3 | 4062 | 4309 | 610,100 B |
| Fe-56 (not) | 3 | 2 | 347 | 850 | 66,209 B |

### 1. Round trip (acceptance bullet 1)

Write with `write_h5`, read back with the existing `load_h5`, compare **every
field with `f64::to_bits`** — exact, no tolerance. A tolerance would be
meaningless: nothing in that path does arithmetic, so any difference is a codec
defect. The evaluation is compared too, at 5 energies x 3 temperatures.

### 2. Cross-code (acceptance bullet 2)

`openmc.deplete`-style cross-code was available here for once:
`WindowedMultipole.from_hdf5` needs **no cross-section library**, only scipy's
Faddeeva. `openmc_inputs/read_wmp.py` reads the file OpenMC's way and prints its
structure and evaluated σ(E, T); the Rust test compares against our own
evaluation of the same record. Floats cross as Python `repr` (shortest
round-trip), so the comparison is not limited by the transport format.

**Tolerance `1e-9` relative, chosen before measuring and deliberately loose.**
The two sides are independent Faddeeva implementations — ours Weideman,
OpenMC's `scipy.special.wofz` — so a bits gate would be wrong. The prediction
recorded in advance was *"near 1e-10 relative, not bits"*. The gate exists to
catch a **broken file**, not to certify the two routines against each other, and
the measured agreement is not used to tighten it.

## Results

### Round trip — exact

Every field bit-identical on both nuclides: name, `fissionable`, `fit_order`,
`awr`, `e_min`, `e_max`, `inv_spacing`, all 4062 (347) poles and their residues,
all curve-fit coefficients, all window bounds and broaden flags. All 15 (E, T)
points per nuclide evaluate **bit-identically** after the round trip.

Four malformed records are refused at write time, each naming its own cause: an
empty name, a residue count disagreeing with the pole count, a curve-fit row
count disagreeing with the window count, and `fit_order < 2` (which OpenMC
refuses outright — better to fail here, where the cause can be stated, than to
write a file whose reader has to guess).

### Cross-code — OpenMC reads it, and agrees

**Structure, read with plain h5py so it is not filtered through OpenMC's own
interpretation:**

```
root attrs: {'filetype': b'data_wmp', 'version': array([1, 1])}
spacing shape () value 0.03281975806835241      <- 0-dimensional, not [1]
data   dtype complex128 shape (4062, 4)         <- complex, not a structured array
windows int32 (4309, 2)   broaden_poly int8 (4309,)   curvefit float64 (4309, 3, 3)
```

**Values:**

| nuclide | values compared | worst relative difference | where |
|---|---|---|---|
| U-238 | 45 | **1.197e-12** | scatter, 100 eV, 293.6 K |
| Fe-56 | 45 | **7.390e-14** | absorption, 1 keV, 1200 K |

Three to four decades inside the gate, and the right *kind* of residual:
nonzero, at the level two double-precision Faddeeva implementations should
differ by. The advance prediction (~1e-10) was met and slightly beaten.

**The physics survives, not merely the structure.** OpenMC's own evaluation of
our file gives U-238's 6.67 eV capture resonance as **7089.9 barn at 293.6 K**
falling to **3952.2 barn at 1200 K** — analytic Doppler broadening through the
poles, which a file that was structurally valid but numerically scrambled could
not produce.

## Two mistakes that would have shipped a file OpenMC cannot read

Both are invisible from this crate's own reader, which accepts either spelling.
**A round trip through this workspace alone would have passed on both.** That is
the argument for the cross-code test rather than the round-trip test, and it is
why the structural facts are asserted on the Python side and pinned in the Rust
test rather than left to the values.

1. **`hdf5-pure`'s `with_complex64_data` helper names its compound fields
   `real` / `imag`.** h5py recognises a two-field f64 compound as `complex128`
   only when the names match its `complex_names` config, whose default is
   **`('r', 'i')`**. Using the convenience helper writes a structurally valid
   file whose `data` h5py hands back as a *structured* array; OpenMC's evaluation
   then fails on arithmetic, nowhere near the real cause. The compound is
   therefore built explicitly with `r` / `i`.
2. **The scalars must be 0-dimensional.** `export_to_hdf5` writes
   `np.array(float)` — a 0-d array — and `from_hdf5` reads
   `group['spacing'][()]`. From a shape-`[1]` dataset that idiom returns
   `array([x])`, and `spacing` then silently becomes an array that broadcasts
   through the whole evaluation. `with_shape(&[])` gives a true scalar
   dataspace.

A third was avoided by reading upstream: the root **`version` attribute is
required** — `from_hdf5` raises `DataError` when it is absent rather than
defaulting — and its major must be 1.

## Known lossiness, stated rather than discovered later

An **empty window** (one with no poles) is held in memory as `start = 1,
end = 0` by `load_h5`, which discards *where* in the pole list it sat. The writer
emits `(1, 0)`. OpenMC iterates `range(windows[w,0] - 1, windows[w,1])`, so
`(1, 0)` and an original `(k+1, k)` both yield no poles and evaluate
identically — the round trip is lossless in **value**, not in **bytes**, and only
for this one field.

This is not hypothetical: U-238's **first window is empty** in the real library
(`windows[0] == [1, 0]` in the file we write). The round-trip test therefore
compares emptiness and then the bounds, rather than the raw pair.

## A defect in this record's own test, found and fixed

The round-trip binary passed in isolation and **failed when run alongside the
cross-code binary**. It was not a flake and it was not the writer: `round_trip`
is called by two tests in the same binary, cargo runs those as parallel threads
of one process, and the scratch path was keyed only on the process id — so both
got the same file and one deleted it while the other was still reading. Adding
another binary to the command changed the timing enough to expose it.

Worth recording for two reasons. First, "passes alone, fails in company" is the
exact signature that gets written off as an infra flake, and the workspace rule
that a failing test is never a flake is what made me look. Second, the first run
of this suite **passed**, so a single green run was not evidence of anything: the
race simply had not lost yet. The path now carries a per-test tag, and the fixed
pair was run three times in combination, green each time.

## Limitations

1. **Two nuclides, not the whole CORE set.** The 125-nuclide library is not swept.
   The two shapes the writer branches on are both covered, but a nuclide with,
   say, a much higher `fit_order` is not.
2. **No `k` comparison.** #270's acceptance text says "produces a `k` consistent
   with the run that produced it". For WMP that is the wrong instrument: a
   windowed-multipole library is not a transport input on its own, and σ(E, T)
   compared directly at 1e-12 is a far tighter statement than an eigenvalue
   compared through two Monte Carlo runs with their own statistics. Recorded as a
   deliberate substitution, not an omission — if a `k` comparison is wanted, it
   needs a full nuclide `.h5` alongside, which is the `nuclide_write` track.
3. **The cross-code test skips without an OpenMC-capable interpreter.** The
   round-trip half is unconditional.
4. **Write only, for one nuclide per file.** OpenMC's `export_to_hdf5` also
   writes one group per call (`mode='a'` appends); a multi-nuclide
   `WMP_Library` bundle is not written here, and `WmpLibrary::pack` remains the
   workspace's own container for that.
