# `outram-blender` vs Blender — upstream port coverage

What this crate covers of Blender's mesh/geometry layer, what it does not,
and which of the gaps are worth closing. Generated by reading the upstream
tree, not by guessing.

- **Upstream:** <https://github.com/blender/blender>, commit
  `786af64aad84154047d93ee077e1fdd1d229f32d`, sparse-checked out at
  `upstream_source/Blender` (gitignored) on **2026-09-19**. Scope:
  `source/blender/bmesh`, `source/blender/blenlib`,
  `source/blender/geometry`.
- **Upstream licence:** GPL-2.0-or-later, GPLv3-compatible. See
  `upstream_source/README.md` for the verification and `NOTICE` for the
  lineage.
- **This crate:** 84 modules, ~44k lines, 514 unit tests + 21 doctests at
  the time of writing, plus 8 headless studio tests in `dhoby-ghaut`.

> **Status is about *presence and provenance*, not correctness.** Nothing in
> this table is human-reviewed V&V. Per the workspace `RESPONSIBLE_USE.md`,
> every row is AI-assisted draft material until a human says otherwise.

## How to read the Status column

| Status | Meaning |
|---|---|
| **PORTED** | Transcribed from the named upstream file, with the GPL attribution header block on the Rust file. Behaviour is intended to match. |
| **REIMPLEMENTED** | Independent Rust implementation of the same concept. No upstream code copied; behaviour may differ and is not claimed to match. |
| **PARTIAL** | Some of the operator's modes or options exist; the rest do not. |
| **MISSING** | No counterpart in this crate. |
| **OUT OF SCOPE** | Deliberately not wanted — see the reason. |

## The gaps, ranked for a solver-mesh frontend

This crate exists to author clean meshes for a CFD volume mesher and a Monte
Carlo CSG bridge. That ranks the gaps differently from how Blender would
rank them — an interactive modelling convenience matters less here than
anything affecting whether a downstream solver can consume the surface.

### Worth closing

1. **`BLI_kdopbvh.cc` — a BVH.** Not an operator, but the boolean and knife
   paths currently do linear scans. This is the difference between a
   demonstration and something usable on a real mesh.
2. **`delaunay_2d.cc` — constrained Delaunay.** Would give `fill`,
   `fill_holes` and the parameterisation path a better tessellation than
   ear clipping alone.

### Low value here

`bmo_circularize`, `bmo_relax_edge_loops`, `bmo_space_edge_loops_evenly`,
`bmo_offset_edgeloops`, `bmo_fill_edgeloop`, `bmo_edgenet`, `bmo_flatten`,
`bmesh_path_region`, `bmesh_region_match` — interactive
modelling aids. A headless authoring frontend driven from code does not
need them, and porting them would add surface area without adding
capability. Listed so the decision is visible, not so it is forgotten.

### Explicitly out of scope

Rendering, media, colour, audio, GPU shading, text layout, UV-space
selection, OpenVDB volumes, and everything in `source/blender` outside
`bmesh`/`blenlib`/`geometry`. `docs/blender-dependencies.md` audits
Blender's third-party stack against the same boundary.

## Verification findings recorded while porting

Reading upstream rather than reasoning from first principles turned up
four things worth keeping. Each is asserted as a test, not just written
down.

| Finding | Where |
|---|---|
| Fan triangulation is **wrong** on concave n-gons — measured +33.3 % area from four of six apex corners on an L-hexagon. This crate did that until 2026-09-19. | `polyfill` |
| `BLI_polyfill_calc` emits **clockwise** triples whatever the input winding; upstream's mesh callers compensate by projecting through the *negated* normal. Missing that inverts every triangulated normal. | `polyfill::polyfill_3d` |
| `bmo_planar_faces`'s `iterations` argument **does not converge** on shared geometry — it plateaus after one sweep and slowly degrades, because each face's target plane is frozen from the input. Re-invoking the operator does converge. | `planar_faces` |
| That operator's `eps = 1e-5` is an **absolute** floor in model units, so a mesh in metres cannot be flattened below ~1e-5 m while the same shape in millimetres flattens a thousand times finer. | `planar_faces` |
| The crate's own one-shot limited dissolve **did not conserve area** (+23.7 % on a 48x32 sphere at 5°) and **silently no-opped** past 15°, because it costed every edge once instead of re-costing after each merge. Now delegates to the port. | `limited_dissolve` |
| Two faces being dissolved commonly share **more than one** edge, so splicing across a single named edge is not enough — it stalls a 3x3 grid at 4 faces. Upstream's `BM_faces_join` cancels the whole shared set; the port does boundary cancellation. | `limited_dissolve::join_faces` |
| `recalculate_normals` decided "outward" by signed volume about the coordinate **origin** — translation-invariant only for closed surfaces. An open bowl at z = -20 came out inverted while the identical bowl at z = 0, 2, 5 or 20 came out correct. | `recalc_normals` |
| **A bug in upstream.** `recalc_face_normals_find_index` computes its area-weighted centroid as `sum(f_cent * area) / (N * total_area)` — the `cent_fac = 1/N` is applied to the accumulator but never to the divisor — so its centre is the true centroid divided by the face count. Verified: a cube of side 2 at (10,0,0) gives (1.667, 0, 0) instead of (10, 0, 0). Invisible in Blender, where meshes sit near their object origin; not invisible here. The port drops the `1/N` and says so. Worth reporting upstream — a maintainer's call. | `recalc_normals` |
| Poke was using upstream's `BMOP_POKE_MEDIAN` while Blender's tool defaults to `MEDIAN_WEIGHTED` — measured 2.415 units apart on a 10-unit face, a quarter of the face. The default now matches, and the other two modes plus `use_relative_offset` were added. | `poke_quads` |
| Concave splitting reaches the optimum (2 pieces) on a single-notch L but only 10-from-14 on a three-notch comb: re-entrant notches force convex boundaries the greedy re-merge cannot cross. "Splits into convex pieces" is not "splits into few convex pieces". | `connect_concave` |

## Maintaining this file

Re-derive it rather than editing by hand where possible:

```bash
# upstream inventory
ls upstream_source/Blender/source/blender/bmesh/operators/
ls upstream_source/Blender/source/blender/bmesh/tools/

# this crate
ls crates/outram-blender/src/
cargo test --release -p outram-blender --lib --tests
```

A row moving from REIMPLEMENTED to PORTED needs the GPL attribution header
block on the Rust file naming the upstream file and commit — that is the
distinction the two statuses record.
