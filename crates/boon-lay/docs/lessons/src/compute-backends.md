## The problem

Every walker in rungs 3–4 is independent of every other. A release
fraction needs tens of thousands of them; an animation needs them advanced a
slice at a time without freezing the screen. How does the crate spread the
work, and which result is trusted?

## Independent streams, so the answer does not depend on the scheduler

Each history $i$ gets its own random-number stream, seeded from a base seed
and $i$ through a SplitMix64 finaliser
([`history_seed`](https://github.com/theodoreOnzGit/outram-park-backend/blob/@@COMMIT@@/crates/boon-lay/src/lagrangian_decay_simulator/lagrangian_diffusion/first_passage/ensemble.rs#@@L:crates/boon-lay/src/lagrangian_decay_simulator/lagrangian_diffusion/first_passage/ensemble.rs:fn=history_seed@@)).
A plain `base + i` would give strongly correlated LCG sequences. With
per-history streams, a run is bit-for-bit reproducible however `rayon`
schedules it, and the test `parallel_run_is_reproducible` pins that.

## Three backends, one physics

[`ComputeType`](../../api/boon_lay/compute/enum.ComputeType.html) picks how an
ensemble advances, by enum dispatch (no trait objects):

| Backend | What it is | Trust |
|---|---|---|
| `CpuSingleThread` (default) | scalar `f64`, one history at a time | **the reference** |
| `CpuMultiThread` | `rayon` across histories, with a [`ThreadCount`](../../api/boon_lay/compute/enum.ThreadCount.html) | acceleration; must match the reference within statistics |
| `Gpu` | a `wgpu` kernel in `f32`, one single-sphere history per GPU thread | acceleration; **unverified** |

## Live, without lagging

[`LiveEnsemble`](https://github.com/theodoreOnzGit/outram-park-backend/blob/@@COMMIT@@/crates/boon-lay/src/lagrangian_decay_simulator/lagrangian_diffusion/first_passage/live.rs#@@L:crates/boon-lay/src/lagrangian_decay_simulator/lagrangian_diffusion/first_passage/live.rs:struct=LiveEnsemble@@)
is the compute core for an animation: a background worker thread owns it,
advances it a slice of simulated time per frame, and publishes a small
`Snapshot` (positions and release fraction) through an `Arc<RwLock<…>>`. The
UI thread only reads the latest snapshot. That is the pattern the workspace's
no-lagging rule asks of every demo, and the `first_passage_realtime` example
uses it.

## In a browser: `wasm_par`

`rayon` does not build for `wasm32-unknown-unknown`. On that target the call
sites import
[`wasm_par`](https://github.com/theodoreOnzGit/outram-park-backend/blob/@@COMMIT@@/crates/boon-lay/src/wasm_par.rs),
serial stand-ins with the same names, so one source tree compiles. For this
crate that is exact, not an approximation: the per-walker work is
independent and the serial path is the trusted reference. The GPU module is
also excluded on wasm, for a type-system reason (wgpu's WebGPU backend is
`!Send` there) described in
[`lib.rs`](https://github.com/theodoreOnzGit/outram-park-backend/blob/@@COMMIT@@/crates/boon-lay/src/lib.rs#L45-L56).
A browser demo therefore runs the CPU path in a Web Worker.

## The checks, and the gap

- `parallel_kernel_release_matches_crank` (ensemble), and
  `cpu_single_and_multi_advance_time_and_agree` (live): the multi-threaded
  path agrees with the reference and with Crank.
- `gpu_selection_is_safe_and_advances`: selecting `Gpu` never fails.
- **The GPU kernel itself is unverified.** It was developed where no adapter
  existed, so only the CPU fallback has run; its `f32` xorshift generator is
  "adequate for a demonstrator". The module says so at the top
  ([`gpu.rs`](https://github.com/theodoreOnzGit/outram-park-backend/blob/@@COMMIT@@/crates/boon-lay/src/gpu.rs#L18-L45)),
  and no number in these lessons comes from it.

**Re-run 2026-10-04** (`develop` atop `5e802df3a4`, `--release`, one core):
all ensemble, live and `wasm_fallback` tests pass, including
`history_seeding_is_independent_of_worker_count`. No machine with a GPU was
used, so the GPU kernel is still unexercised.
