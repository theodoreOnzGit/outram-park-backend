# The "kovan folder" project format — design (op-63u0)

Status: **design only, not implemented.** This document is the deliverable
for kopi-beans `op-63u0`, split from GitHub issue #30's second comment. It
must land (and get maintainer sign-off) before `op-b1y5` (implementation),
`op-9vml` (bibliography window) and `op-wr08` (structured markdown GUI
editing) start.

## 1. What the maintainer asked for (verbatim structure)

> I want kovan to be able to work in custom folders containing bibliography
> and literature files. Under the root folder ... `kovan.toml`, `my
> bibliography.bib` (user-named), a pdf folder, a markdown folder, git files
> (if it is a git repo). ... `kovan.toml` is an index file which points to
> the bib entry, the pdf, and the markdown — down to the line numbers ...
> Kovan should autogenerate these line numbers and update kovan.toml
> whenever, based on a standard markdown structure. Kovan should be able to
> read and write the individual markdowns via GUI, add or remove
> information, but should not be able to change the structure.

So: a **user-pointable** folder (any path on disk, not this workspace's own
`crates/kovan-literature/`), shaped like:

```text
<project-root>/
├── kovan.toml            # generated index — see §3
├── <user-named>.bib      # the one bibliography file, name chosen by the user
├── pdf/                  # raw PDFs, one per document
├── markdown/             # processed per-document Markdown, standard sections
└── .git/                 # optional — present if the folder is a git repo
```

## 2. Reconciling with the existing "Canonical Representation" rule

`docs/kovan.md` § "Canonical Representation" is explicit: *"Only the Rust
struct is authoritative... Do not make: BibTeX, TOML, Markdown metadata
authoritative."* `kovan.toml` as specified above is unmistakably meant to be
a **generated index** — every field it holds (bib key, PDF path, markdown
path, section line ranges) is derivable from the `.bib` file, the PDF's
presence on disk, and the markdown file's own section markers. So:

**`kovan.toml` is generated, never hand-authored, and never read as an
input to anything but a locate-by-line-number operation.** The same pattern
this workspace already uses for `crates/kovan-literature/CATALOGUE.md`
("maintained through `kovan`, not by hand" — root `CLAUDE.md`) applies here
unchanged: a human (or another tool) may open and read `kovan.toml`, but the
only writer is `kovan`'s own regeneration pass (§4), and any edit made
outside that pass is silently clobbered on the next regeneration — exactly
like `CATALOGUE.md`. This must be stated in `kovan.toml`'s own header
comment when `op-b1y5` implements it, the same way generated files elsewhere
in this workspace say so (e.g. `docs/<crate>-api.md`'s "regenerated, not
hand-edited" convention).

**What *is* authoritative**, per document, in order:

1. The `.bib` entry — one BibTeX record is still the canonical bibliographic
   metadata for that document (title/authors/year/etc.), consistent with
   `kovan_literature::bibtex::to_bibtex` already being a *render*, never a
   *parse-back*, function.
2. The markdown file's own section content (§3.2) — authoritative for
   summaries/full-text/CSV bodies.
3. The PDF file itself — authoritative for the source artifact; nothing
   derives *from* `kovan.toml` back into the PDF.

`kovan.toml` sits **downstream** of all three, never upstream of any of
them — it is a cache, not a database.

## 3. `kovan.toml` schema

TOML (not JSON) because it is meant to be occasionally hand-*read* by a
person or another tool navigating the project (the "efficiently index this
kovan folder" goal from the issue) even though it is never hand-*written*.

```toml
# GENERATED FILE — do not edit by hand. Regenerated by `kovan` whenever a
# markdown file under markdown/ changes, or on explicit `kovan-cli
# project regen`. Edits made here are overwritten without warning.
schema_version = 1
bib_file = "my bibliography.bib"   # relative to this file's directory

[[document]]
id = "argonnecodecenter1977anl7416"   # matches the .bib entry's cite key
pdf = "pdf/anl-7416-supplement-2.pdf"
markdown = "markdown/anl-7416-supplement-2.md"

[document.sections]
# Each key is a standard section name (§3.2); value is the 1-indexed,
# INCLUSIVE line range [start, end] within `markdown`, covering that
# section's heading line through its last content line before the next
# section heading (or end of file).
ai_summary       = [4, 22]
author_summary   = [24, 31]
full_text        = [33, 812]
table_csvs       = [814, 900]     # may be absent (no tables) — key omitted
graph_csvs       = [902, 940]     # may be absent (no digitised plots)
```

- `[[document]]` is an array-of-tables, one per document in the project —
  mirrors how a `.bib` file itself is a flat list of entries.
- `document.id` **must** equal the `.bib` entry's cite key — this is the
  join key across all three files (bib / pdf / markdown), and it is how the
  bibliography window (`op-9vml`) jumps from a `.bib` row to its PDF and
  markdown.
- A missing optional section key (no digitised tables/plots yet for that
  document) is simply absent, not written as `[0, 0]` or similar — matches
  this workspace's general "don't fabricate a zero" data-honesty posture.
- Paths are relative to `kovan.toml`'s own directory, forward-slash,
  portable across the Android/Termux + desktop split this workspace already
  maintains for everything else.

## 4. The standard markdown structure

One markdown file per document, under `markdown/`, holding the sections the
issue names: **AI summary, author summary, full text (from OCR or AI),
table CSVs (from digitised tables), graph CSVs (from digitised plots)**.

### 4.1 Section markers

Each section starts with a fixed-text HTML comment marker, not a plain
Markdown heading — a heading's *text* is something a human editing content
might reasonably want to change ("## Summary" → "## Author's Summary"),
which would break line-number tracking and blur the "structure vs content"
line the issue draws. A comment marker is inert to a markdown renderer and
unambiguous to `kovan`'s own regeneration parser:

```markdown
<!-- kovan:section ai_summary -->
## AI Summary

*(model-generated; not reviewed)*

The reactor is a ...

<!-- kovan:section author_summary -->
## Author's Summary

...

<!-- kovan:section full_text -->
## Full Text

...

<!-- kovan:section table_csvs -->
## Digitised Tables

### Table 3

```csv
x,y
1,2
```

<!-- kovan:section graph_csvs -->
## Digitised Graphs

### Fig. 7

```csv
x,y,x_minus,x_plus,y_minus,y_plus,origin
...
```
```

- Section **order is fixed** (as listed above) and every generated file
  contains every marker, in that order — a section with no content yet is
  still present, with an empty body, so `op-b1y5`'s regeneration pass can
  always find all five markers by a single top-to-bottom scan and never
  needs to invent a line range for a section it can't locate.
- `table_csvs`/`graph_csvs` bodies are themselves one subsection (`###`) per
  digitised artefact, each holding one fenced ` ```csv ` block — this is
  the same CSV text `DigitisedDataset::to_csv_string()`
  (`crates/kovan/src/digitiser/dataset.rs`) already produces for the plot
  digitiser, and the shape `op-hnhp`'s table digitiser should reuse rather
  than invent a second convention for the same idea.

### 4.2 GUI content-vs-structure contract (`op-wr08`)

"Kovan should be able to read and write the individual markdowns via gui,
add or remove information, but should not be able to change the structure."
Concretely, for `op-wr08`'s editor:

- The five `<!-- kovan:section X -->` marker lines, their fixed order, and
  the section heading text immediately following each marker are
  **read-only** in the GUI — not shown as editable text at all, only as
  section labels/tabs the user picks between.
- Everything **between** one marker (inclusive of the heading line) and the
  next marker (exclusive) is a free-text (or, for the two CSV sections,
  free-`###`-subsection) edit region.
- On save, the editor writes back only the body text within the section
  boundaries it was given — it never emits a marker line itself. If the
  boundaries it was handed are stale (the file changed on disk since the
  editor opened it — e.g. a fresh digitisation appended a new `###`
  subsection to `graph_csvs`), the save is rejected with a conflict message
  instead of silently overwriting, rather than trusting an in-memory line
  range that may no longer point at the right place.
- This makes `op-wr08` a **consumer** of `kovan.toml`'s line ranges, not a
  second parser of the marker syntax — it opens a document by reading
  `kovan.toml`'s `document.sections` table for the ranges, slices the
  markdown file at those lines, and hands the operator only the slice.

## 5. Line-number regeneration

**Trigger:** any write to a file under a project's `markdown/` directory —
whether from `op-wr08`'s GUI editor, a future `kovan lit import` targeting
this project, or a digitiser export landing its CSV into a section. Not
polled, not on a timer; fires synchronously at the end of whichever
operation just wrote the file, the same "write, then refresh the index"
shape `kovan_literature`'s `extract_metadata` → `to_bibtex` pipeline already
has (bibtex is *rendered*, never cached stale).

**Algorithm** (per changed markdown file):

1. Read the file, scan top-to-bottom for `<!-- kovan:section NAME -->`
   marker lines (`NAME` restricted to the five known keys — an unknown name
   is a parse error, not a silently-ignored line, since a typo'd marker
   would otherwise produce a document with a "missing" section that isn't
   actually missing).
2. For each marker at line `L`, its section's range starts at `L`0F (the
   marker line itself, so a reader/writer always has the heading in view)
   and ends at the line immediately before the next marker (or EOF for the
   last section).
3. Missing optional sections (no `table_csvs`/`graph_csvs` marker present
   at all — the document has no digitised tables/plots) simply produce no
   entry in `document.sections` for that key, per §3's "don't fabricate a
   zero."
4. Re-serialise the whole `kovan.toml` (all documents, not just the changed
   one — cheap, since it's a handful of TOML tables, and avoids any
   incremental-patch logic that could drift from a full rescan).
5. Write atomically (temp file + rename), matching how this workspace's
   other generated-index writers (e.g. `CATALOGUE.md`'s regenerator) avoid
   leaving a torn file behind a crash mid-write.

**Regeneration never inspects file *content* beyond the marker lines** — it
does not re-parse CSV bodies or re-render anything; it is purely a
line-counting pass. This keeps it fast enough to run synchronously on every
markdown write without a noticeable GUI stall.

## 6. Relationship to this workspace's own literature archive

`docs/kovan.md` § "Storage Layout" already describes `open/` /
`proprietary/` / `generated/` under `crates/kovan-literature/` — this
repository's own internal literature archive, fixed in location, used by
`kovan-cli lit` and the TUI's Literature/Ingest tabs.

**These are two different things, and the "kovan folder" format does not
replace or subsume the internal archive.** The internal archive's `open/`
vs `proprietary/` split exists for a reason specific to this workspace — an
open-source public repository that must never commit proprietary content —
which does not generalise to an arbitrary user-pointed folder (a personal
research folder on a laptop has no "must be committable" constraint at
all). Concretely:

- The internal archive stays exactly as it is: `open/`/`proprietary/` source
  trees, `generated/markdown|bibtex|assets/`, driven by
  `kovan_literature::storage::{generated_dir_for, root_for}`.
- A "kovan folder" is a **separate, general-purpose** project shape a user
  points `kovan` at via a path — most commonly *not* inside this workspace
  at all (a personal literature folder, a project-specific one for a paper
  being written, etc.).
- **This workspace's own internal archive is not planned to become "one
  instance of a kovan folder."** Forcing the internal archive's fixed,
  compliance-driven layout to fit the generalised schema (a single `.bib`,
  one `markdown/` folder with no open/proprietary split) would either break
  the compliance split or complicate the general format to accommodate a
  special case only this repository needs. They stay two concepts: the
  internal archive is `kovan-literature`'s own fixed convention;
  the kovan-folder format (this document) is `op-b1y5`'s new, general,
  user-pointable one. A future bridge (e.g. "export this workspace's `open/`
  tree as a kovan folder for external sharing") is plausible but explicitly
  out of scope here — not asked for, and would need its own design pass if
  wanted.

## 7. What `op-b1y5` needs to implement (not done in this design pass)

- The `document.sections` regeneration scanner (§5) — pure function, easy
  to unit-test against synthetic markdown fixtures (mirrors this crate's
  existing "synthetic self-consistency" testing style, e.g. the digitiser's
  `tests/digitiser_synthetic.rs`).
- `kovan.toml` (de)serialisation via `serde`/`toml` — `toml` is not yet a
  dependency of this crate; check the workspace `[workspace.dependencies]`
  table first per the "search before building" hard rule (several other
  crates in this workspace likely already pin a `toml` version).
- A "new kovan folder" scaffolding action (writes the empty `pdf/`,
  `markdown/` directories and an empty `<name>.bib`) for `op-9vml`'s
  bibliography window to offer as "create a project here."
- Wiring `kovan-cli` with a `project` subcommand group (`kovan-cli project
  regen <path>`, mirroring the `kovan.toml`-regeneration trigger for
  headless/CI use, matching every other generated-artifact convention in
  this crate having both a GUI/TUI path and a scriptable CLI path).

## 8. Open questions for the maintainer

1. **Bib-key collisions.** If two documents in the same project would
   generate the same cite key (e.g. two 1977 ANL reports with the same
   first author), what should happen? `kovan_literature`'s existing slug
   generation doesn't need to solve this today (each document lives in its
   own `open/`/`proprietary/` subtree, keyed by path); a shared single
   `.bib` file makes it a real question for `op-b1y5`.
2. **Multiple documents sharing one PDF** (a bound volume, a proceedings
   PDF with several papers) — out of scope for this design pass; the schema
   above assumes one PDF ↔ one markdown ↔ one bib entry.
3. **What happens to `table_csvs`/`graph_csvs` provenance** (calibration,
   review status, operator) when a CSV block moves from a `DigitisedDataset`
   JSON into a markdown fenced block — is the full JSON provenance record
   kept alongside (e.g. as a sibling section, or a linked file), or does
   embedding into markdown deliberately drop it down to "just the numbers"?
   The issue's own spec says "CSVs from digitised plots" without further
   detail; recommend keeping the full JSON as a sibling file
   (`markdown/<doc>.graph-fig7.json`) that the markdown section links to by
   relative path, so the provenance record (`DATA_POLICY.md`'s digitisation-
   is-a-processing-step rule) is never silently dropped — but this is a
   recommendation, not a decision, and should be confirmed before `op-b1y5`
   starts.
